# Эксперимент: выборочная оптимизация compute SPIR-V

> **Предупреждение: кандидат `feaa68b92e2af0bc` (№ 8) больше не рекомендуется.** Пользователь сообщил о зависании драйвера на R7 260X после его включения. Оставьте `OptimizedComputeHash8=` пустым и восстановите сохранённую DLL/INI от предыдущей конфигурации. Локальные валидатор и тесты не гарантируют безопасности GPU.

Меню при `HeavyComputeWords=61000` появилось, но фон на `Menu.png` практически чёрный. В одном журнале кадры продолжали выводиться; устойчивость во всех сценах и причина прежнего зависания не доказаны. Несколько compute-пайплайнов размером от 61000 слов заменяются заглушками; часть может быть нужна для сцены, но это не установлено. Отключение таких проходов само по себе может приводить к чёрной картинке. При этом возможны и другие проблемы: эмуляция RT, совместимость драйвера, отсутствующие функции и т. д.

Этот эксперимент **не просто сжимает файл**. Он использует `spirv-opt -Os`, чтобы попытаться упростить уже преобразованный прокси SPIR-V. Меньше слов не означает меньшую нагрузку на GPU или более быструю компиляцию. `spirv-val` проверяет корректность SPIR-V, но не доказывает эквивалентность изображения, корректность взаимодействия с игрой, успешную компиляцию и выполнение на R7 260X. Возможны зависание драйвера или компьютера и повреждённая графика. Сохраните работу и сделайте копию предыдущей локальной DLL и INI. Не меняйте системную DLL, TDR и настройки реестра.

## 1. Получить модули, не изменяя поведение рендеринга

Соберите DLL с файлами `dllmain.cpp`, `optimized_compute.h` и остальными заголовками из ветки. Здесь Windows/MSVC и GPU не тестировались. Поместите DLL только рядом с игрой, где уже стоит прокси. В **рабочем INI игры** сохраните успешные настройки и установите:

```ini
[spirv]
HeavyComputeWords=61000
KeepShaderCode=1
DumpHeavyCompute=8
OptimizedComputeHash=
OptimizedComputeHash2=
OptimizedComputeHash3=
OptimizedComputeHash4=
OptimizedComputeHash5=
OptimizedComputeHash6=
OptimizedComputeHash7=
OptimizedComputeHash8=
```

Другие значения не меняйте. По умолчанию `DumpHeavyCompute=0`, а пустые `OptimizedComputeHash`, `OptimizedComputeHash2`, `OptimizedComputeHash3`, `OptimizedComputeHash4`, `OptimizedComputeHash5`, `OptimizedComputeHash6`, `OptimizedComputeHash7` и `OptimizedComputeHash8` не активируют оптимизацию. Значение dump ограничено до 16 разных модулей за запуск; размер каждого — до 8 МиБ. Эти файлы содержат преобразованный код шейдеров игры. Не публикуйте их, если не хотите делиться игровыми данными. В каталоге игры появятся файлы `spv_heavy_<16 hex>_0.spv` и строки `SPIRV-OPT-SAMPLE` с исходным и итоговым числом слов. Уже существующие файлы не перезаписываются. Файлы сохраняются только для соответствующих пропущенных пайплайнов, для которых доступен код; карантин/FAKE-модуль может отсеять другие случаи раньше.

Сохраните лог и один или несколько файлов `spv_heavy_*.spv`. Используйте файлы именно этого запуска и этой конфигурации — хеш зависит от всех преобразований прокси. Если отправляете их для анализа, выбирайте те, для которых в логе указан исходный размер около 61000–64000 слов. После сбора установите `DumpHeavyCompute=0`.

## 2. Оптимизировать один файл отдельно

Установите Vulkan SDK с `spirv-opt` и `spirv-val` в `%VULKAN_SDK%\Bin`, а также Python 3. В PowerShell из каталога исходников, заменив путь на **реальный файл из шага 1**, запустите:

```powershell
python .\tools\optimize_heavy_compute.py 'F:\ПУТЬ_К_ИГРЕ\spv_heavy_ХЕШ_0.spv' --limit 61000
```

Скрипт сначала проверяет вход через `spirv-val --target-env vulkan1.2`, затем использует `spirv-opt -Os` с сохранением bindings, интерфейса и specialization constants, затем снова выполняет `spirv-val`. Если проверка не проходит, версия или имена compute entry point изменились, либо результат не уменьшился и не стал **строго меньше 61000 слов**, кандидат не устанавливается. Это может произойти для всех образцов: автоматически работающих вариантов пока нет. Файлы в `spv_opt` не перезаписываются. При успехе записывается `spv_opt\spv_<хеш входа>.spv` рядом с исходным файлом и выводится точное значение настройки `OptimizedComputeHash`.

Скрипт требует флаги `--preserve-bindings`, `--preserve-interface` и `--preserve-spec-constants`; если SDK слишком старый и не поддерживает их, скрипт завершится с ошибкой и файл не установит. Можно указать явные пути `--spirv-opt` и `--spirv-val`.

### Если модуль использует scalar block layout

При диагностике 8 присланных модулей обычный валидатор отверг все 8: шесть требуют более свободной укладки блоков, а два имеют другую ошибку (локальные `OpVariable` стоят после обычных инструкций). Нельзя пропускать ошибку структуры или использовать `--skip-validation`. Поддержка `scalarBlockLayout=1` в строке `REAL Vulkan12Features` **не означает**, что приложение включило функцию при создании устройства. В новом журнале это не было видно.

Для проверки теперь логируется значение `SCALAR-LAYOUT: sanitized Vulkan12Features.scalarBlockLayout=...` перед `vkCreateDevice`; только значение `1` вместе с успешным результатом `vkCreateDevice` в том же запуске подтверждает включение через Vulkan 1.2 struct. Если строка отсутствует, этот путь не подтвердился; отдельный extension struct автоматически не распознаётся. Прокси не включает функцию этим изменением и не проверяет её при выборе кандидата — ответственность за проверку остаётся у пользователя.

**Только если функция включена в целевом запуске**, при диагностике `improper straddle` можно явно добавить `--scalar-block-layout` к команде. Флаг передаётся обоим вызовам `spirv-val` и внутреннему валидатору `spirv-opt`. Он не включает возможность устройства и не исправляет другие ошибки. Результат применим только к соответствующей конфигурации и точному хешу преобразованного модуля.

С SPIRV-Tools v2026.4 шесть образцов прошли до и после оптимизации при этом условии. Например, `845f4527681546ce`: 62142 → 29988 слов, `97f71c5fce8223ec`: 62817 → 33426. Это размеры уже преобразованных модулей, не размеры исходных шейдеров игры. Два других образца (`a478b6161a40eeca`, `ec2514354f42e082`) не прошли из-за порядка `OpVariable` даже с этим флагом; их кандидаты не создавались. Даже прошедшая валидация не доказывает включение нужных возможностей устройства, эквивалентность или стабильность на GPU.

## 3. Начать с одного кандидата — только осознанно

В рабочем INI укажите `OptimizedComputeHash=<16 hex из вывода скрипта>`, оставив `HeavyComputeWords=61000`, `KeepShaderCode=1` и `DumpHeavyCompute=0`. В ходе запуска прокси применяет кандидат только к одному точному хешу **текущего преобразованного compute-модуля**, если его исходный размер попадает под порог. Минимально проверяются SPIR-V-структура, версия, имена compute entry points и размеры; эти проверки **не** заменяют `spirv-val`. Кандидат, отказавший при `vkCreateShaderModule`, откатывается на базовый модуль с прежним ограничением. Имеющиеся карантин/таймаут компиляции сохраняются; они не защищают от зависания GPU при выполнении и не могут гарантировать корректное восстановление драйвера.

Один и тот же модуль может использоваться в нескольких пайплайнах или с разными specialization constants, поэтому один хеш не равен обязательно одному пайплайну. Другие модули по-прежнему подпадают под `HeavyComputeWords`. Оптимизированный модуль может иметь другой хеш карантина. Изменения других INI, например SWRT или переписывания, приводят к несовпадению хеша; вариант, который драйвер принял лишь после внутреннего fallback-переписывания, может не совпасть с хешем до создания модуля — тогда эксперимент не применяется.

После отдельного испытания первого модуля можно **осознанно** добавить второй точный хеш в `OptimizedComputeHash2` (по умолчанию пустой). Нужен отдельный `spv_opt\spv_<второй хеш>.spv`; первый хеш и файл остаются на месте. Дополнительно доступен третий точный хеш `OptimizedComputeHash3`, также выключенный по умолчанию; его стоит включать только после отдельного наблюдения за первыми двумя. Четвёртый `OptimizedComputeHash4` тоже выключен по умолчанию; проверяйте новые варианты по одному, а не одновременно. Пятый `OptimizedComputeHash5` тоже выключен по умолчанию. Шестой `OptimizedComputeHash6` тоже выключен по умолчанию. Седьмой `OptimizedComputeHash7` тоже выключен по умолчанию. Восьмой `OptimizedComputeHash8` тоже выключен по умолчанию. Максимум восемь выбранных хешей, каждый проходит те же проверки размера, entry point и отдельного файла; проверка не является полной SPIR-V-валидацией. Включение второго оставляет первый активным, увеличивая совокупную нагрузку и риск зависания. Это не доказывает работу второго или исправление графики. Если второй вызывает проблемы, очистите только `OptimizedComputeHash2` и восстановите ранее рабочие DLL/INI.

В логе ищите `SPIRV-OPT: testing selected`, `SPIRV-OPT: allowing selected compute pipeline`, а затем `SPIRV-OPT: selected pipeline driver result=...` или сообщения о карантине, toxic signature и таймауте. `allowing` означает только прохождение ограничения по размеру, не успешное создание пайплайна. Результат драйвера относится ко всему batch; успешное создание и ненулевой handle также не доказывают выполнение на GPU. Дополнительно проверяйте `HEAVY-FAKE`, ошибки компиляции и `FRAMES`. При ухудшении немедленно прекратите тесты, очистите все восемь `OptimizedComputeHash`, `OptimizedComputeHash2`, `OptimizedComputeHash3`, `OptimizedComputeHash4`, `OptimizedComputeHash5`, `OptimizedComputeHash6`, `OptimizedComputeHash7` и `OptimizedComputeHash8` и верните предыдущую DLL/INI. Не увеличивайте порог и не отключайте общую защиту для этого эксперимента. Никакого гарантированного исправления меню пока нет.

## Эксперимент: сохранение capability для двух graphics-модулей

В паре `spv_gpfail10_stage1_0.spv` и `spv_gpfail10_stage10_0.spv` из пользовательского архива валидатор SPIRV-Tools v2026.4 (`--target-env vulkan1.2 --scalar-block-layout`) отверг оба модуля: в них используются форматы storage image `Rg16f` и `R16f` без `OpCapability StorageImageExtendedFormats` (49). На пути переписывания RayQuery прокси безусловно вырезал capabilities 46 и 49; прежний лог отмечает cap49 в исходных модулях. При добавлении **только** capability 49 в копии двух дампов оба прошли проверку. Это не доказывает, что ошибка пайплайна `-13` вызвана только этим, что другие возможности включены, или что результат работает на GPU.

Для ограниченного теста DLL содержит выключенный по умолчанию opt-in: `GraphicsCap49VertexHash` и `GraphicsCap49FragmentHash`. Патч добавляет declaration capability 49 только в точно совпавший уже преобразованный vertex/fragment-модуль; другие шейдеры и `HeavyComputeWords` не изменяются. Если `shaderStorageImageExtendedFormats` не передана включённой в успешный `vkCreateDevice`, устройство не совпадает, хеш не совпал или минимальная проверка не прошла, патч не применяется. Прокси не включает функцию самостоятельно. После отказа `vkCreateShaderModule` выполняется повтор с прежним модулем. Карантин и прочие защиты остаются включёнными, но не гарантируют защиту от зависания GPU или драйвера.

Только для конкретной присланной пары и её конфигурации:

```ini
[spirv]
GraphicsCap49VertexHash=4ff26a9ff4ef23ad
GraphicsCap49FragmentHash=e4f5b7cee57c69e4
```

Сначала сохраните DLL/INI и работу, затем пересоберите DLL со всеми заголовками (`graphics_cap49.h` обязателен). Остальные параметры и выбранный compute-кандидат оставьте как в предыдущем запуске. В логе ищите `GRAPHICS-CAP49: sanitized shaderStorageImageExtendedFormats=1 deviceResult=0`, `testing selected` и `pipeline result`. Последнее относится к реальному вызову драйвера до возможного fallback и не доказывает выполнение GPU. Если строки `testing selected` отсутствуют, хеши на этой конфигурации не совпали и тест ничего не поменял. Изменения настроек переписывания, порядка и версии игры могут изменить хеш. При ухудшении очистите оба значения и восстановите прежнюю DLL/INI.

Проверены C++-helper, условия выбора и откат в локальных тестах с моками, а также оба результата настоящим `spirv-val`. Windows/MSVC, драйвер и R7 260X не тестировались. Эксперимент может вызвать нестабильность или зависание и не является готовым исправлением графики.

## Наблюдение после graphics-capability эксперимента

В последнем пользовательском тесте оба выбранных graphics-модуля были модифицированы, `shaderStorageImageExtendedFormats=1`, но драйвер многократно вернул `-13` при создании соответствующего графического пайплайна. Отключить эксперимент можно, очистив `GraphicsCap49VertexHash` и `GraphicsCap49FragmentHash`.

## Дампы около порога 61000

## Пятый кандидат

Лог после четвёртого эксперимента подтверждает создание всех четырёх выбранных compute pipeline драйвером (result=0); это не доказывает GPU-выполнение. При сохранении настроек предлагается отдельно испытать `31c3054863d5ea27` (исходный игровой код 61581 слов, преобразованный дамп 62573 → 30310 слов). Проверка валидатором требует `scalarBlockLayout`, а предыдущий запуск сообщал `scalarBlockLayout=1` и успешное создание устройства. Драйвер и GPU не испытаны; увеличение числа одновременно активных шейдеров может повысить риск зависания. Общий лимит не повышать, при ухудшении убрать пятый хеш и восстановить сохранённые DLL/INI.

## Шестой кандидат

Лог после пятого эксперимента показывает создание всех пяти выбранных compute pipeline драйвером (result=0); это не доказывает их GPU-выполнение. После создания пятого pipeline была остановка кадров не менее 108 секунд по таймеру watchdog, затем кадры возобновились. В общей сложности есть 216 залогированных ошибок graphics pipeline и 5 compute; 20 HEAVY-FAKE — ограниченный журнал, не полное количество. Причина задержки и влияние отдельного шейдера не установлены.

Для отдельного добровольного теста шестым предложен `e2a8b03e23650220`: 71828 исходных слов, преобразованный дамп 78711 → 49423 слов; валидация до и после оптимизации требует `scalarBlockLayout`. Он больше предыдущих кандидатов; размер не предсказывает время компиляции, нагрузку и стабильность. Включение шестого увеличивает совокупный риск зависания, не гарантирует корректную картинку и не заменяет исправление graphics failures. Сохраняйте копии текущих DLL/INI и не повышайте общий лимит; при ухудшении очистите шестой хеш и верните предыдущие версии.
